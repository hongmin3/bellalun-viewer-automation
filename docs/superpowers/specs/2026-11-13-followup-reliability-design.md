# BellalunAuto 후속 안정화와 회귀 완료 후 자동 닫기 설계

상태: 2026-11-13 사용자 승인. P1~P14 전체와 GUI 자동 닫기. 실행마다 원상복원 여부 선택.
근거: #132 조사 결과, f247d21, SPEC REQ-QA-001/002/005, REQ-WU-002, REQ-REGRESSION-002.

## 목적과 범위

저장 실패에도 실제 수행 결과를 보존하고, 시험 전 데이터 보존과 자원 점검을 공통 실행 경로에 적용한다. 회귀 완료 후 사용자가 자리를 비웠으면 60초 뒤 BellalunAuto 창을 닫는다.
사용자가 P1~P14 전체와 GUI 자동 닫기 구현을 승인했다. 시험 후 원상복원은 실행마다 선택한다.

## 검토한 접근과 제안

- 회차별 임시 감독 스크립트 확장: 일반 GUI/CLI 사용자가 같은 보호를 받지 못하므로 채택하지 않는다.
- 공통 실행 계층에 백업·기록·점검을 통합: 이번 제안. GUI와 CLI가 같은 보호를 받고 단위시험에서 실패를 재현할 수 있다.
- 서버 원격 실행부터 전환: 신뢰성 문제가 원격으로 확대되고 인프라 결정이 필요해 뒤 순서로 둔다.

사용자가 확정한 동작: 회귀 완료 후 60초 자동 닫기, 자동 닫기 멈춤 버튼, 다른 버튼 조작 시 자동 닫기 취소.
아래 세부 정책에 따라 구현하며 실제 설치/제거와 제품 UI 수용은 구체 계획을 제시한 뒤 승인받는다.

## 1. GUI 자동 닫기

대상 파일: bellalunauto/gui.py, 새 bellalunauto/auto_close.py, tests/test_distribution_gui.py, 새 tests/test_auto_close.py.

- 기본기능과 실시간 WU의 실행 기록 저장이 끝나고 status=completed인 경우에만 시작한다. 제품 FAIL 때문에 엔진이 1을 반환해도 정상 완주면 대상이다.
- 비정상 종료, 사용자 중단, UAC 취소, 준비 점검 명령은 자동으로 닫지 않는다. 오류를 읽을 시간을 보장한다.
- 별도 상태 줄에 ‘회귀가 끝났습니다. 60초 뒤 창을 닫습니다.’와 남은 초를 표시한다. 기존 결과 요약은 유지한다.
- ‘자동 닫기 멈춤’ 버튼을 항상 보이되 카운트다운 중에만 활성화한다. 누르면 해당 회차의 자동 닫기를 영구 취소한다.
- 준비 점검·기본기능·WU·PC별 설정·결과 폴더·수동 검토·공유 ZIP·버전 등 모든 GUI 버튼은 콜백 실행 전에 자동 닫기를 취소한다. 키보드 Space/Enter에 의한 버튼 실행도 같은 래퍼를 통과한다.
- 단순 마우스 이동·로그 선택은 취소 조건으로 추가하지 않는다. 사용자가 창 닫기를 직접 누르면 기존 즉시 종료 동작을 유지한다.
- 새 회귀가 끝나면 새 60초를 시작한다. 이전 after 콜백은 취소하고 세대 번호를 확인해 재실행/취소 뒤 늦은 콜백이 창을 닫지 못하게 한다.
- 타이밍은 monotonic deadline과 Tk after로 처리한다. UI 스레드를 sleep으로 막지 않는다. 59.999초에는 열려 있고 60초 이상이면 닫힌다.
- 카운트다운은 시험·리포트·선택한 복원 작업·최종 실행 기록 저장이 모두 끝난 뒤에만 시작한다. 복원 중에는 completed로 취급하지 않는다. 창 종료는 이 최종 저장 이후에만 허용한다. 자동 닫기가 Viewer나 서비스 종료 명령을 추가 실행하지 않는다.

검증: 가짜 시계·스케줄러로 60초 경계, 취소, 새 실행, 늦은 콜백을 시험한다. GUI 콜백 연결은 제품을 실행하지 않는 Tk 창 시험으로 버튼/키보드 취소와 실제 destroy를 검증한다.

## 2. 저장 실패 시 결과 보존과 실행 기록

대상: run.py, core/wu_chain.py, core/automation_health.py, bellalunauto/runs.py, bellalunauto/app.py, 기존 test_wu_chain/test_qa_runs 관련 시험.

- 기존 WinError 5/32/33의 최대 8회/1.95초 제한 재시도를 재사용한다. 무한 재시도하지 않는다.
- 단계 결과는 저장 시도 전에 메모리 결과 모음에 편입한다. 저장 실패 시 다음 제품 단계로 진행하지 않고 부분 리포트 작성과 종료 정리를 수행한다.
- 부분 리포트는 chain_completed=false, 실패 단계와 비밀정보를 제거한 오류 종류·번호를 담는다. 정상 완주·릴리스 게이트는 이 리포트를 받지 않는다.
- 기본 회귀의 진행 기록 쓰기 실패도 이미 끝난 결과를 버리지 않는다. 보고서 저장 자체도 실패하면 별도 비상 JSON 저장을 시도하고 실패를 표면화한다. 모든 디스크 쓰기가 실패하면 영속 보존을 보장할 수 없다고 명시한다.
- checkpoint.finish 실패와 보고서 작성 전 실패를 구분한다. 완료 표식이 없는 저장점의 재개를 별도 상태 검사 없이 허용하지 않는다.
- GUI는 작은 진행 기록을 읽고 큰 WU 저장점 반복 읽기를 제거한다. 진행 기록 읽기 실패는 제품 시험의 FAIL 판정으로 바꾸지 않는다.
- 감독 프로세스가 실행 번호로 최종 상태를 저장한다. GUI는 디스크 상태를 다시 읽어 표시하며 오래된 메모리로 최종 기록을 덮어쓰지 않는다.
- 고아 실행 확인은 PID와 프로세스 시작 시각·실행 번호를 함께 사용한다. 확인할 수 없으면 임의로 종료/완료 처리하지 않는다.

검증: 지속 파일 잠금, 접근 거부, 진행 쓰기 실패, 마지막 단계 저장 실패, finish 실패, GUI 없는 종료, 오래된 GUI 기록, PID 재사용을 실패 주입으로 확인한다.

## 3. 백업·복원과 내용 증명

대상: 새 core/run_preservation.py, run.py의 공통 실행 경계, bellalunauto/runplan.py와 동의 화면, 새 tests/test_run_preservation.py.

- 공통 실행 전에 이번 실행의 DB·변경 가능 폴더·QC·Dose SR 포함 이미지·XIPL 파라미터·USB 시험 폴더의 보존 범위를 계획으로 만든다. 폴더 중복·대상 밖 링크·원본 안 백업 목적지는 거부한다.
- 사전 manifest에 경로별 존재 여부·크기·SHA-256을 기록한다. 내용 복원이 필요한 모든 기존 파일은 백업 사본의 해시까지 대조한 뒤 제품 실행을 허용한다.
- 백업 위치는 제품 데이터와 분리된 작업 폴더의 실행 번호별 경로를 기본 제안으로 한다. 용량이 부족하면 위치를 사용자가 선택하게 하고 실행을 차단한다.
- 기존 Baseline 복원 기능과 시험 전 상태 복원을 구분한다. 시험 후 DB를 사전 상태로 복원하는 기능은 기존 일반 사용자 정책을 바꾸므로 동의 화면에 명시하고 사용자 승인 후 적용한다.
- 정상/중단/예외 모두 정리 경계를 통과한다. 강제 종료·재부팅은 다음 시작 시 미완료 복구 기록으로 감지하고 새 시험 시작을 차단한다. 자동 복구를 추측 실행하지 않는다.
- 복원 상태는 확인/사전 사본 없음/불일치/복원 오류를 구분한다. 과거 QC 6개와 초기 Dose SR은 새 백업으로 복구됐다고 표시하지 않는다.
- 사전/사후 양방향 목록과 내용 해시를 대조한다. 실행 중 생성 파일은 삭제하지 않고 실행 보관소로 옮겨 보존한다. 원본 사본과 증거는 자동 삭제하지 않는다. 제품 데이터에서 생성 파일을 보관소로 옮길 때 보고서가 참조하는 증거를 먼저 보존하고 링크를 보관소 경로로 연결해 끊어진 증거 링크를 만들지 않는다.
- manifest·백업 경로·복원 결과를 실행 번호 및 보고서에 연결한다. DB 확인은 비교한 테이블/열 범위를 명시하고 전체 바이트 일치로 표현하지 않는다.

검증: 같은 크기·같은 시각의 내용 변경, 추가/삭제 파일, 빈 폴더, 링크, 읽기 실패, 복원 실패, 사본 누락, 중간 종료를 임시 폴더에서 시험한다. 실제 DB/파일 복원 수용은 별도 승인된 회귀에서 확인한다.

## 4. 자원 사전 점검

대상: core/env_preflight.py, 공통 실행 진입점, core/run_preparation.py, GUI 준비 화면, 관련 기존 시험.

- 기본기능/WU/단독 USB의 같은 실행 경계에서 메모리를 확인한다. 기존 1 GiB 미만 BLOCK, 2 GiB 미만 WARN을 유지한다.
- 제품 데이터·백업·작업·USB가 같은 볼륨이면 예상 증가량을 합산하고, 다른 볼륨이면 각각 계산한다. 백업량은 실제 사전 파일 크기에서 계산한다.
- 제품 디스크 경고 12 GB는 과거 관측값이다. 공식 고정 기준이라고 선언하지 않고 설정 가능한 보수적 운영 여유와 생성량 예약값으로 분리해 계획에 표시한다.
- 예상량 미확정·용량 조회 실패는 준비 미확인으로 시작을 막고 근거를 안내한다. 기존 자료 삭제로 자동 해결하지 않는다.
- 보관 도구는 복사→파일별 해시 대조→명시적 이동 순서다. 목적지 용량과 원래 경로 연결을 검증하고 손상/부분 복사를 성공으로 보지 않는다.

검증: 부족/정확한 경계/충분, 공유 볼륨, 조회 불가, USB 분리, 복사 중 실패, 해시 불일치. 실제 디스크를 채우거나 제품 경고를 유발하지 않는다.

## 검증과 완료 기준

- SPEC 신규 요구사항과 TEST 추적성을 구현 전에 추가한다. 기존 사양 미충족은 올바른 사양을 유지한다.
- 단위시험 RED→GREEN, 전체 pytest, 프로젝트 정적·추적성 검사, cleanup-workspace와 readiness/workspace gate를 수행한다.
- 이번 공통 실행 계층 변경은 기본기능+WU 두 묶음에 영향이 있다. 빌드한 EXE로 두 묶음 수용을 제안하며, 과거 실측 기준 합계 약 175분에 백업/복원 시간이 추가된다.
- 실물 실행 전에 빌드 신원·예상 시간·입력 점유·DB/설정·USB·원상복원 계획을 제시하고 사용자 답변을 기다린다. 현재 C/D 여유는 대용량 백업·빌드·회귀에 부족할 수 있어 재측정한다.
- 독립 검토 뒤 관련 SPEC/CHANGELOG/progress/README를 갱신한다. 인계 원문과 민감자료는 공개 저장소에 넣지 않는다.
- 모든 요구사항이 검증되기 전 완료라고 보고하지 않는다. 검증된 변경은 기존 사용자 AGENTS.md 변경을 제외해 커밋·일반 push한다.
## 설계 검토 결과
독립 builder 검토 완료. 사용자가 전체 범위와 실행별 원상복원 선택을 확정했다. 복원 완료 후 타이머 시작 및 보관 이동 후 증거 링크 보존 지적은 본문에 반영했다.
