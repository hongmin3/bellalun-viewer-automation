기존 README.md, 구조 문서, automation_scope.json, traceability.json과 테스트에 근거한 최소 현재 사양이다. 기존 자동화 엔진과 팀원 PC용 BellalunAuto 배포 실행 계층을 다룬다. 컴파일·설치·실제 제품 시험의 검증 범위는 각각 결과 기록으로 구분한다. 현재 제품 작업의 우선순위와 남은 결정은 NEXT_WORK.md에 둔다. 사양과 구현이 다르면 SPEC / CODE MISMATCH로 보고한다.

1. 목적

Bellalun Viewer의 기준 QA 체크리스트를 실제 UI로 수행하고 검증 가능한 PASS/FAIL 근거를 남긴다. 성공 조건은 체크리스트의 대상·의미를 유지하면서 자동화 한계와 실제 제품 결함을 구분해 보고하는 것이다.

한눈에 보기

사람이 설치된 BellalunAuto의 화면이나 명령으로 체크리스트(기본기능 또는 Windows Update)를 고르면, 자동화가 실행 환경과 관리자 권한을 확인한 뒤 Bellalun Viewer를 실제 UI로 조작한다. 화면·DB·파일에서 근거를 모아 기대 결과와 대조하고, 체크리스트 문맥에 맞는 판정 리포트를 남긴다.

2. 프로젝트 범위

포함

  • 기본기능 체크리스트의 Workflow와 기능군별 시나리오 및 문서화된 회귀.
  • 기존 기본기능/XIPL 결과를 이용하는 Windows Update 전용 흐름과 리포트.
  • TC별 자동화 범위·사양 근거 추적성, 판정 및 생성 증거.
  • Python·Git·소스가 필요 없는 Windows x64 팀원용 실행파일·설치 프로그램과 설정 화면.
  • 상위 지식 폴더를 검증 자료 관리 서버의 최신 판으로 맞추는 동기화(받는 PC에서만).

제외

  • 비슷한 이름의 다른 체크리스트로 TC 번호/절차를 대체하는 작업.
  • 근거가 없는 PASS, 미확정 Release Note/OS 기준값의 추정, WU_09 완료의 미검증 승격.
  • 승인된 시험 흐름 밖의 DB 복원·설정 변경 및 비공개 원본의 공개 저장소 편입.
  • 회귀 밖 독립 설치 패키지 점검을 기본 회귀에 임의 편입하는 작업.

3. 시스템 구성

run.py가 명령·환경 gate·회귀를 연결한다. TC 시나리오는 tests에, UI/OCR·DB·DICOM·판정·보고 공용 계층은 core에 있다.

core/result.py가 판정과 공통 리포트 데이터를 담당하고 core/winupdate_report.py가 Windows Update 체크리스트 출력을 담당한다.

automation_scope.json과 traceability.json은 각각 범위와 근거 연결의 데이터 원본이다. 비공개 체크리스트·지식·Baseline은 auto Git 저장소 밖 자산이다.

bellalunauto/는 GUI·작업 경로·중복 실행·자식 감시를 맡고 기존 엔진을 호출한다. 설치 위치의 resources는 읽기 전용 자료다. 설정과 생성물은 설치 폴더 아래 작업 폴더에 둔다(소스 실행은 고른 작업 폴더).

4. 전체 동작 흐름

  1. 기준 체크리스트와 범위에 맞는 명령을 선택하고 실행 환경/권한을 확인한다.
  2. 선택한 흐름의 선행조건과 문서화된 회귀 순서를 따른다.
  3. 제품 UI 동작을 수행하고 화면·DB·파일·수신 결과 등 근거를 관찰한다.
  4. 기대 결과와 대조해 TC/Step 상태와 이유·증거를 기록한다.
  5. 기본기능 또는 Windows Update 문맥에 맞는 제목·원본 문서·판정 리포트를 생성한다.

목적

기본기능과 Windows Update 리포트가 각각의 제목·기준 문서·판정 이유를 보존한다.

입력

TC/Step 결과, report title/source document/source sheet 메타데이터, expected/actual/note. 구조화된 기대값·실제값은 JSON의 expected_data·actual_data에도 보존한다. HTML은 복잡한 값을 접어 펼칠 수 있는 항목별 표로 표시한다. 시간 기록이 있는 TC는 단계 이름·소요 초·완료 또는 오류 상태를 표시한다.

선행 조건

선택한 실행 흐름의 리포트 문맥이 제공된다.

동작

공통 HTML/TXT/CSV/JSON 리포트에 실행 환경·명령·TC 판정과 사유를 전달한다. Windows Update는 기본기능 제목으로 오표기하지 않는다. 체크리스트 결과에서 Fail/Manual의 이유를 전용 Comment에 쓰고 기존 수기 공용 Comment를 덮어쓰지 않는다.

HTML·TXT 리포트 맨 앞에 "결론 — 한눈에 보기"를 둔다(사용자 요청 2026-11-05).

  • 결론 한 문장: 성공·실패·사람 확인 건수와 새 실패가 있는지. 색으로 성공/주의/실패를 나눈다.
  • PASS가 아닌 TC마다 한 줄: 결과, 멈춘 Step과 확인 항목, 기대값과 실제값, 원인.
  • 원인은 등록된 알려진 결함이면 그 결함 설명, 아니면 판정 근거의 첫 문장이다. 리포트가 원인을 추측해 만들지 않는다.
  • 알려진 결함 판별은 릴리스 게이트와 같은 분류 함수(classify_fail)를 쓴다.

기대 결과

두 리포트의 기준 문서와 판정 이유가 혼동되지 않고 실패/미검증 사유를 읽을 수 있다.

하는 일

소스의 단위시험·정적 검사 뒤 검증용 빌드를 만들고, 설치판으로 승인받은 범위를 시험한 결과가 배포 기준을 채웠는지 확인한다. 소스 UI 회귀와 설치판 UI 회귀를 연달아 반복하도록 요구하지 않는다.

순서

  1. 설치판 실행 기록의 EXE·build-info·리포트를 다시 읽고 해시, 시험 시작 이후 생성 여부, 선택한 명령과 범위가 맞는지 본다. 설치 파일 검증이 끝났고 모든 선택 실행이 완료돼야 한다. 리포트의 출처는 build-info여야 한다.
  2. 리포트 meta의 source_commit이 빌드 커밋과 같고 source_dirty가 false인지 본다. 리포트는 실행할 때 이 값을 남긴다(소스 실행은 Git, 설치판은 build-info).

    • 실행 시작 때 값도 함께 읽는다. 시작 때 커밋(source_commit_at_start)이 리포트 때와 다르거나 시작 때부터 수정이 있었으면 source_dirty를 참으로 남긴다.

    • WU 재개(--resume)는 처음 실행의 시작 값을 저장점에서 읽어 쓴다. 설치판은 작업 폴더가 저장소여도 EXE 옆 build-info 값을 쓴다.

  3. WU를 선택했으면 실시간 실행이고 체인을 끝까지 수행했으며 PASS 10 / SKIP 3(사람이 직접 하는 WU_01·12·13, REQ-VERDICT-002)인지 본다.
  4. 기본기능을 선택했으면 전체 회귀인지, KNOWN_DEFECT_EXCLUDE 밖의 FAIL·BLOCKED가 없는지, SKIP이 사람이 직접 하는 TC(WF_16)뿐인지 본다. 단독 TC는 지정한 TC가 모두 포함됐는지와 같은 판정 기준을 확인한다.
  5. 선택하지 않은 묶음의 리포트는 요구하지 않는다. 승인 기록에 시험 범위·미수행 범위·EXE 해시를 남긴다. 부분 시험 통과를 전체 회귀 통과로 표시하지 않는다.

결과

python tools/release_gate.py --installed-verification <기록> --scope <범위>가 항목별 통과·실패와 거부 사유를 보여 준다. 통과 후 같은 EXE를 배포하며 다시 컴파일하지 않는다. 후보 파일명과 build-info는 보존하고 별도 배포 승인 기록으로 검증을 연결한다. 기존 --wu --basic과 빌드의 --gate-wu --gate-basic은 과거 전체 회귀 기록 호환용이다.

안 될 때

게이트 입력이 없거나 통과하지 못해도 후보 빌드는 만든다. 산출물 이름에 -candidate를 붙이고 게이트-미통과-후보.txt와 build-info에 사유를 남긴다.

하는 일

Setup 설치 → 설치된 BellalunAuto 실행 → 준비 점검 → 사용자가 고른 시험 순서로 쓴다. 각 단계는 실제 결과만 보여 준다. 설치나 화면 열기만으로 DB 복원·제품 시험을 시작하지 않는다.

순서

  1. Setup은 관리자 권한을 요구한다. UAC를 취소하거나 관리자 권한을 얻지 못하면 설치하지 않는다. Setup 안의 한국어 관리자 확인 창은 추가 방어다. 실제로 보이는 화면은 실측 결과로만 배포 안내에 적는다.
  2. 완료 화면에서 "BellalunAuto 열기"를 고를 수 있다. 화면은 설치를 시작한 원래 사용자 권한으로 연다. 제품을 조작하는 시험은 시작할 때 UAC로 관리자 권한을 받는다. 시작 메뉴·바탕화면·직접 실행도 같다.
  3. 같은 버전 재설치와 새 버전 업데이트는 기존 설치 위치에 덮어쓴다. 설치 폴더의 resources는 새 판으로 통째로 바꿔 이전 판 자료가 섞이지 않게 한다. 작업 폴더의 설정·결과·증거·로그는 그대로 둔다.
  4. 첫 실행은 작업 폴더 선택 창과 PC별 설정 창을 띄우지 않는다(사용자 결정 2026-11-05). 찾은 값으로 설정을 저장하고 바로 준비 점검을 보여 준다.

    • Viewer 위치: Windows 프로그램 목록(이름 Bellalun)에서 위치가 하나로 정해질 때만 쓴다.

    • 데이터 폴더: 고정 디스크의 BellalunData 중 Config·Database가 있는 하나만 쓴다. USB의 같은 이름 폴더는 쓰지 않는다.

    • SQL: 등록된 인스턴스 중 이름이 BELLALUN인 것을 쓴다. XIPL은 XIPL_PATH, OCR은 PATH와 기본 설치 위치에서 찾는다.

    • 서버 주소·시험 계정: 사내 배포본의 팀 공통 설정(resources/team-settings.json)을 먼저 넣고, 이 PC에 있던 BellalunAuto 설정(기억한 작업 폴더, 기본 작업 폴더)이 있으면 그 값을 쓴다. 추측하지 않는다.

    • 찾지 못한 값은 준비 점검에 [FAIL]로 보이고 [PC별 설정]에서 채운다.

  5. 준비 점검의 첫 줄은 "시작 전에 해결할 문제 N개" 또는 "시험을 시작할 수 있습니다"다. 일반 권한으로 연 화면의 권한 행은 실패가 아니라 안내로 표시하고 종료 코드에 넣지 않는다.
  6. 점검 문구는 실제 결과에 맞춘다. 경로가 비어 있으면 "미설정", 적힌 위치에 파일이 없으면 "위치에 없음"으로 나눈다. Tesseract가 없으면 설치를 안내한다. XIPL_PATH가 실패하면 XIPL 하위 행에 그 원인을 먼저 해결하라고 적는다.

결과

설치 성공·화면 열림·준비 점검 통과·제품 시험 결과를 서로 다른 사실로 남긴다. 미확인 항목을 준비 완료로 표시하지 않는다.

안 될 때

  • 설정 파일이나 작업 폴더 기억 파일이 손상되면 화면이 조용히 꺼지지 않는다. 오류 창에 파일 위치와 원인을 보이고 손상 파일은 덮어쓰지 않는다.
  • 작업 폴더 기억이 손상되면 작업 폴더를 다시 고르게 한다. 새 폴더를 고른 경우에만 손상 파일을 preferences.json.손상-<날짜>로 보관하고 새 값을 쓴다.
  • 설정 파일이 손상되면 파일을 바꾸지 않고, 고치거나 이름을 바꾼 뒤 다시 열도록 안내한다.
  • 복구를 취소하면 기존 파일을 바꾸지 않는다.
  • 시험을 시작할 때 UAC를 취소하면 "시험을 시작하지 않았고 제품·DB는 바뀌지 않았다"고 알리고 종료 코드 1223으로 끝낸다.

  1. 실행하는 동안 PC가 절전이나 화면 꺼짐에 들어가지 않게 한다. Windows 전원 설정은 바꾸지 않는다.
  2. 단계마다 시간 상한을 두고 Viewer가 계속 응답하지 않는지(SendMessageTimeoutW, SMTO_ABORTIFHUNG, 120초 연속) 감시한다.
  3. 넘으면 실패 증거를 남기고 Viewer를 끝낸 뒤, 그 단계의 TC를 BLOCKED와 사유로 기록한다.
  4. 다음 단계는 USB 실패 뒤와 같이 Viewer를 다시 띄워 계속한다. 전제 단계(기준 DB 복원·DICOM 서버 설정·화면 계약)가 FAIL·BLOCKED면 체인을 멈춘다.
  5. 단계가 끝날 때마다 work/winupdate_checkpoint.json에 결과를 원자적으로 저장한다(임시 파일에 쓴 뒤 바꿔 넣는다).
  6. run-winupdate --resume은 저장점의 완료 단계 결과를 다시 쓰고 남은 단계만 실행한다. 리포트 meta에 resumed·reused_stages·stage_trips를 남긴다.

설정

단계별 시간 상한은 config.json > winupdate.stage_timeouts로 바꿀 수 있다. 기본값은 core/wu_chain.py의 STAGE_TIMEOUTS다.

안 될 때

저장점이 없거나, 내용 해시가 맞지 않거나, 체인 구성이 다르거나, 이미 끝난 체인이면 재개하지 않고 종료 코드 2로 알린다.

지킬 것

지식 폴더에 서버와 같은 문서가 있고, 서버에 없는 로컬 자료(텍스트 캐시·작성 규칙 문서 등)는 그대로 남는다. 실행 기록은 상위 logs/knowledge-sync/<날짜>.log에 남는다.

9. 오류 처리 정책

  • 환경 gate 실패를 무시하고 UI 입력을 계속하지 않는다.
  • 기대/실제 불일치는 FAIL, 자료/자동화 한계는 근거가 있는 MANUAL, 미수행은 해당 흐름의 SKIP으로 남긴다. BLOCKED는 해제 조건과 미검증 범위를 보존한다.
  • 실제 재현된 실패만 해당 실행의 이슈로 보고하며 알려진 제품 결함을 자동화 성공으로 숨기지 않는다.
