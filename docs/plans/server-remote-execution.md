# 공용 서버 원격 실행 전환 계획 (추후 고도화)

**상태:** 계획만 있음. 구현·SPEC 요구사항·실제 PC 검증은 하지 않았다(2026-11-11 사용자 요청으로 정리).
**Goal:** 테스트 PC마다 EXE를 설치하지 않고, 공용 QA 서버 한 곳에 둔 자동화 코드를 서버에서만 제어해 각 테스트 PC에서 실행하고 결과를 서버 웹에서 본다.
**범위:** BellalunAuto 우선 계획. VXvue 자동화도 같은 방식을 쓸 수 있으며 먼저 적용할 제품은 착수 때 정한다.

## 왜 바꾸는가

- 변경 빈도가 높다. 2026-10-11~11-11 커밋 89건, 2026-11-10~11-11 이틀 사이 1.0.7~1.0.11 후보 5개를 빌드했다(`CHANGELOG.md`).
  수정마다 빌드 → 회귀 → 팀원 PC 재설치를 반복하면 실제 PC들은 지난 판을 쓰게 된다.
- 같은 서버(10.13.0.222)를 이미 DICOM Storage SCP(`config.example.json`의 `storagescp`)로 쓰고 있어 시험 기반이 이미 그 서버에 걸려 있다.
- 서버에서 한 번 고치면 다음 실행부터 모든 PC에 반영되고, 어떤 판으로 돌렸는지 서버 한 곳에 남는다.

## 기존 서버에서 확인한 사실 (2026-11-11, 읽기 전용 GET만)

`http://10.13.0.222:5050/`(VHD 원격 Child/Master 관리)은 Ubuntu의 Flask(Werkzeug, Python 3.12) 앱이다.
페이지 설명대로 서버가 테스트 PC에 **WinRM으로 직접 접속**해 작업한다. PC 준비는 최초 1회 `/download/Host_Bootstrap.bat`
관리자 실행뿐이다(WinRM 활성화·방화벽 허용·`LocalAccountTokenFilterPolicy=1`·Hyper-V). 이후에는 웹에 PC IP·관리자 계정을 넣고
`/api/jobs`로 진행을 본다. PC에 상주 프로그램이 없다. 서버 소스는 이 PC에 없어 내부 코드는 확인하지 않았다.
같은 날 `/api/server-status` 기준 디스크 여유 약 84GB(사용률 84%), 메모리 8GB 중 약 5.5GB 여유, 5050·5002·5003 포트 사용 중이었다.

## 핵심 제약과 해결 방향

- **WinRM 세션에는 데스크톱이 없다.** 그대로 실행하면 화면 캡처·클릭·OCR이 실패한다.
  서버가 WinRM으로 "로그인한 사용자 세션에서 도는 예약 작업"(Interactive, 최고 권한)을 등록하고 즉시 시작한다.
  관리자 권한으로 실행되므로 REQ-DIST-006의 UAC 확인 창 없이 시작해야 하는 별도 실행 모드가 필요하다.
- 테스트 PC는 로그인 상태이고 화면이 잠기지 않아야 한다. 서버가 실행 전에 확인하고 조건이 안 되면 사유와 함께 거부한다.
  원격 자동 로그온 설정은 비밀번호가 레지스트리에 남으므로 보안 검토 전에는 하지 않는다.
- 코드는 Python이므로 서버가 휴대용 Python(embeddable)·의존 패키지·Tesseract를 PC 작업 폴더에 복사한다. 해시가 같으면 다시 보내지 않는다. PC에 설치·PATH 변경은 없다.

## 구조

```
공용 QA 서버 (새 포트, 별도 프로세스·가상환경)
  ├─ 자동화 코드 묶음 (판별 해시, candidate / stable 채널)
  ├─ 휴대용 Python·패키지·Tesseract
  ├─ 작업 DB · 실행·진행·결과 웹 화면
  └─ WinRM 실행기
        ① 접속 → 로그인·잠금·실행 중·VHD 작업 여부 확인
        ② 코드·런타임 동기화(해시 비교)
        ③ 사용자 세션 예약 작업 등록·시작
        ④ 진행 이벤트·로그 수집 → 웹 실시간 표시
        ⑤ Reports·Evidence 회수, 예약 작업 정리
```

## 배포 정책 판단

| 항목 | EXE 빌드·배포 (현재) | 서버 코드 (전환 후) |
|---|---|---|
| 수정 반영 | 빌드 → 배포 → PC마다 재설치 | 승격 즉시 다음 실행부터 전체 PC |
| 잘못된 수정의 영향 | 설치한 PC만 | 모든 PC에 한 번에 퍼짐 → 채널·승격 게이트로 막는다 |
| 서버 장애 | 영향 없음 | 실행 불가 |
| 외부·폐쇄망 PC | 가능 | 불가 |
| 재현성 | 산출물 고정 | 판별 묶음을 해시로 보관해야 같은 수준 |

결정: **사내 테스트 PC는 서버 코드 방식, 외부·폐쇄망은 기존 EXE를 유지한다.** EXE는 마일스톤 때만 빌드한다.
빌드는 없어져도 릴리스 게이트는 유지한다. `docs/distribution-guide.md`의 릴리스 게이트(REQ-DIST-005)를 통과한 판만
`stable`로 승격하고, 실행 기록에는 그때 쓴 코드 해시를 남긴다. 되돌리기는 `stable`이 가리키는 판을 바꾸는 것이다.

## 단계와 예상 기간

| 단계 | 내용 | 예상 |
|---|---|---|
| 1. 서버 앱 | 새 포트 Flask 앱, 작업 DB·상태 기계, 실행·목록·진행 화면, 결과 보관, PC별 잠금 | 3~5일 |
| 2. 원격 실행기 | WinRM, 세션·잠금 확인, 코드·런타임 동기화, 사용자 세션 예약 작업, 로그 수집, 취소·강제 중지·정리 | 3~5일 (가장 불확실) |
| 3. Bellalun 실행 모드 | 실행 인자 파일 입력, JSON Lines 진행 이벤트, 확인 창 없는 실행, PC별 설정 | 1~2일 |
| 4. 실제 PC 검증 | Bellalun 설치 PC에서 처음부터 끝까지, 실패·취소·잠금 상황 포함 | 2~3일 |
| 5. 운영 정비 | 채널·롤백, 계정 관리, 결과 보관 기간, SPEC·문서·시험 | 2~3일 |

첫 제품 실제 실행 확인까지 약 2주, 두 제품·운영 정비까지 3~4주로 본다.
늘어날 요인: 회사 보안 정책의 WinRM·예약 작업 차단, Bellalun 설치 PC 확보, 공유 서버의 패키지 설치 제한(별도 가상환경 필요).

## 영향 범위

| 대상 | 영향 | 위험·대책 |
|---|---|---|
| 공용 서버 | 새 프로세스·포트 1개, 런타임 수백 MB, 결과 누적 | 디스크 사용률 84%. 로컬 `Evidence/`만 217MB이므로 보관 기간·용량 상한이 필수 |
| 기존 서비스 5050·5002·5003 | 코드·프로세스 분리로 직접 영향 없음 | CPU·디스크 공유 |
| VHD 관리 웹(5050) | 수정하지 않는다. `/api/jobs`를 읽어 VHD 작업 중인 PC에는 실행하지 않는다 | 재부팅 충돌 방지 |
| 테스트 PC | Bootstrap을 이미 실행한 PC는 추가 준비 없음. 작업 폴더·임시 예약 작업만 생긴다 | 자동화 동작(DB 복원·서비스 재시작)은 지금과 같다 |
| 이 저장소 | 실행 모드 진입점·진행 이벤트 추가. EXE 경로·판정·회귀 순서는 유지 | 기존 단위시험으로 회귀 확인 |
| 운영 | 서버 반영·`stable` 승격 절차가 새로 생긴다 | 승격 게이트를 건너뛰지 않는다 |

## 착수 조건과 보호할 것

- 착수 전 필요: 서버 SSH 접근과 배포 위치, 서버 앱 저장소 위치, Bellalun이 설치된 테스트 PC, 전용 실행 계정 정책.
- 착수 시 먼저 SPEC에 요구사항(REQ ID)과 시험을 정의한 뒤 구현한다. 이 문서는 사양이 아니다.
- 관리자 비밀번호를 저장소·로그·결과에 남기지 않는다. 서버 저장이 필요하면 암호화와 접근 범위를 먼저 정한다.
- 판정 기준·TC 매핑·회귀 순서·DB 복원 정책을 바꾸지 않는다. 바뀌는 것은 실행을 시작하고 결과를 모으는 경로뿐이다.
