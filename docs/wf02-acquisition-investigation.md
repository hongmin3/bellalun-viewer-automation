# WF_02 3D-W 촬영 대기 조사

2026-11-06 후보8의 기본기능 회귀 실패를 조사했다. **자동화는 생성 중인 3D-W 결과를 너무 일찍 판정했다.** Viewer의 DB 시간 초과가 왜 발생했는지는 별도 문제이며 원인을 확정하지 않았다. 제품의 성능 정상 여부를 이 조사로 승인하지 않는다.

`SPEC / CODE MISMATCH`: REQ-REGRESSION-001은 수행 범위와 관찰 결과에 맞는 판정을 요구한다. 기존 구현은 현재 촬영의 세 결과가 생성 중인데 75초에 부족한 건수를 최종 판정했고, 다른 그룹의 결과를 구분하지 않았다. 올바른 기대값을 유지하고 CODE를 수정한다.

## 기대와 실제

WF_02의 3D-W 확장은 Send 시험에 필요한 픽스처를 만든다. 기대값은 기존과 같은 `InstanceType {0:1,1:2,2:2,3:2}`다. 개정 체크리스트 본래 범위의 2D·3D-N 판정과 3D-N의 Series/Group·UID 검증도 유지한다.

후보8 기본기능 실행에서 3D-W는 22:59:27.285에 시작했고, Raw 최초 저장은 22:59:34.111이었다. 23:00:02.741에 Viewer의 `QueryTargetExposureIndex` DB 시간 초과가 기록됐다. Raw가 추가된 뒤 Recon/Syn은 23:00:47·51에 추가됐으며, Viewer 완료 신호는 23:00:52.461, 진행 표시 종료는 23:00:52.481이었다. 시작부터 종료까지 85.196초다.

자동화는 F8 반환 직후부터 최대 75초 동안 전체 검사 건수를 폴링했다. 판정값은 `{0:1,1:2,2:1,3:1}`이었다. 이후 같은 실행의 Send·Export는 3D-N/3D-W의 Recon 2건을 확인했다. 영상이 영구 누락된 상황과 자동화가 조기 판정한 상황을 구분해야 한다.

## 가설별 판단

| 가설 | 근거 | 판단·한계 |
|---|---|---|
| 자동화 대기 기준 문제 | `workflow02.DB_TIMEOUT=75`; Viewer 완료 85.196초; 실제 `workflow02.run` 경로에서 84초 도착을 재현하면 기존 코드 FAIL | 확인. 건수 상태 폴링 자체는 있었지만 완료 전에 상한에 도달했다. 전체 건수는 이번 촬영 그룹의 완료를 구분하지도 못한다. |
| 자동화 DB 폴링이 Viewer 쿼리를 차단 | `core/db.py`는 조회마다 별도 PowerShell·연결을 사용하고 명시 트랜잭션 없이 `SqlDataAdapter.Fill`, `finally Close`를 수행한다. 조회는 INSTANCE의 검사별 집계다. | 연결·트랜잭션을 폴링 사이에 유지하는 결함은 확인되지 않았다. 최초 실패 시점 SQL 대기·잠금 자료가 없어 당시 차단 여부를 배제하거나 자동화 원인으로 확정할 수 없다. 단독 진단에서 별도 수집한다. |
| 제품·SQL 환경 지연 | Viewer의 실제 DB 시간 초과 1건과 이후 처리 완료 | 지연 사건은 확인. DB 시간 초과 자체의 제품/SQL 환경 원인은 미확정이다. 자동화의 조기 판정 결함과 함께 존재할 수 있다. |
| GPU 상태 차이 | 실패 실행과 같은 후보 WU 통과 실행 모두 `No GPUS`; WU의 3D-W는 32.903초 완료 | GPU 부재만으로 이번 FAIL 차이를 설명하지 못한다. 드라이버·장치·OS 설정을 바꾸지 않는다. |

후보8 설치판 단독 진단은 Baseline 복원·DICOM 설정·WF_01 준비 후 04:05~04:11에 실행했다. 종료0, WF_02 PASS27/FAIL0이며 3D-W는 약33.7초에 완료됐다. GPU 오류 조건은 같았고 원래 지연은 재현되지 않았다. SQL DMV를 0.5초 간격으로 준비 포함1423회 수집했으며, WF_02 구간의 활성 요청45행에서 차단 요청은0, 최장 요청은3670ms였다. 이 진단에서 30초 차단은 관찰되지 않았지만 과거 DB 시간 초과의 원인을 배제하는 증거는 아니다.

## 실측 시간과 선택한 대기

Viewer 로그 27개와 WF_02 보고서 17개를 읽고, 촬영 시작 `System State Change(2)`부터 마지막 진행 종료 신호까지 연결했다. 도중 로그가 없거나 두 신호를 연결할 수 없는 촬영은 수치에 포함하지 않았다. 보고서가 중복 보관된 경우 시작·완료·판정으로 중복을 제외했다. WU 내부 호출은 별도 로그 구간으로 비교했다.

| 모드 | 연결된 촬영 수 | 최소 | 중앙값 | 최대 | 75초 초과 |
|---|---:|---:|---:|---:|---:|
| 3D-N | 117 | 21.120초 | 22.379초 | 65.152초 | 0 |
| 3D-W | 90 | 20.882초 | 22.714초 | 85.196초 | 1 |

WF_02에 연결된 3D-W 10건은 21.417~85.196초였다. 실패 건의 Raw 최초 저장부터 종료까지도 78.370초여서 Raw 도착만으로 완료로 간주할 수 없다. WU 통과 대조군(01:08:48.514~01:09:21.417)은 Raw부터 종료 31.295초였으며 GPU 오류 조건은 같았다. 이 분포는 보관된 로그 범위의 실측이며 제품 성능 요구사항이 아니다.

수정은 기존 `core/viewer_processing.wait_new_group`을 재사용한다. F8 전에 그룹 키를 보관하고, 현재 촬영으로 생긴 새 그룹에 Raw/Recon/Syn이 모두 들어와야 대기를 끝낸다. 기존 공용 상한 180초는 실측 최대 85.196초를 포함한다. 고정 180초를 자거나 시간만 지나면 성공시키지 않으며, 영구 누락은 타임아웃과 실제 건수를 기록하고 FAIL한다. 건수가 맞아도 새 그룹이 완성되지 않으면 FAIL한다.

`workflow05`는 새 촬영 없이 기존 영상을 사용하는 경로다. `workflow07`, `system_compat`의 촬영과 `xipl_flows`의 3D-N/W 촬영은 이미 새 그룹 대기를 쓴다. Send는 WF_02 픽스처를 사용하며 자체 촬영 대기가 없다. 따라서 공용 DB 조회나 전체 TC의 상한을 넓히지 않고 WF_02의 3D-N/W 촬영만 통일한다. 2D 대기는 유지한다.

## 검증과 근거 보존

`tests/test_workflow02_acquisition.py`는 실제 `workflow02.run`을 실행하되 외부 UI·SQL만 가상화한다. 지연 도착 2종과 이전 그룹에만 결과가 추가되는 경우는 수정 전 실패를 확인했다. 영구 누락, 촬영 skip, 빠른 완료를 함께 검사한다. 기존 건수 기대값은 가상 DB가 반환한 독립 데이터로 대조한다.

원본 로그·보고서·SQL 진단 자료와 SHA-256·분포 상세는 Git 제외 작업 폴더에 보존한다. 사내 원문·환자 영상·설정은 공개 저장소에 넣지 않는다. 후보8 설치판 단독 진단, 수정 후 단위시험·설치판 전체 회귀·배포 게이트의 결과는 `progress.md`와 설치 인수표에 각각 기록하며, 이 설계 설명만으로 완료 처리하지 않는다.
